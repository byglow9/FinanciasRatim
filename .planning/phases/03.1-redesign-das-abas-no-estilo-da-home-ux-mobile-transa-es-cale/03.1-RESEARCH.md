## Summary

O recorte exato do ciclo (UX-09) é menor do que o CONTEXT sugere: o núcleo (`cycleOf`, `shiftCycle`, `billOccurrences`, `cycleMonths`, `billsForCycle`) e o serviço `getTransactionsInRange(person, start, end)` já existem e já alimentam a Home. O que falta é (a) um hook de janela estável por `cycle.key` (o `now` do `CycleContext` renova a cada minuto), (b) serviços de intervalo para eventos, aportes de metas e saldo acumulado até `cycle.end`, (c) tirar `useTransactions`/`useFixedExpenses`/`CalendarPage` do mês-calendário e (d) trocar a chave de pagamento de "mês em que o ciclo começa" para "mês da ocorrência" (hoje a página de Contas Fixas e a Home divergem quando o ciclo cruza dois meses). **Nenhum índice novo é necessário**: as consultas têm o mesmo formato dos índices `(ownerId, person, date DESC)`, `(ownerId, date DESC)` e `(ownerId, date ASC)` já em `firestore.indexes.json`, e a guarda `firestore-config` exige exatamente 19 índices.

Os maiores riscos não são de dados, e sim de decisão de produto e de guardas: (1) o sketch do Calendário tem setas de mês próprias, mas o app tem um único seletor de ciclo no topo e o `CycleContext` proíbe ciclo futuro (clamp em 0), enquanto uma agenda precisa olhar para frente; (2) a escala tipográfica 12/16/28/56 e pesos 400/700 da Fase 3 é incompatível com os sketches (11, 13, 14, 15, 22, 44px e peso 800) e é imposta por guarda estática nos arquivos do dock e dos primitivos; (3) pelo menos 8 guardas estáticas citam texto exato dos arquivos que serão reescritos (tabela na seção 3); (4) o núcleo não pode conter a palavra `fixedExpense` em código (guarda `fixed-expense-manual`), então os módulos novos usam `bill`.

Quatro telas (Relatórios, Metas, Porquinho, Login) não têm sketch: o plano deve tê-las como portões `checkpoint:human-verify` em paralelo à Onda 1, para o dono escolher enquanto o código-base é preparado. O Login se sobrepõe a IDEN-08 (Fase 5): nesta fase só o visual Moeda e os alvos de 44px, sem nome Coinki, sem onboarding.

**Primary recommendation:** Entregar em 4 ondas: (W1) núcleo puro + testes, primitivos novos e dock, mais os portões de sketch das 4 telas em paralelo; (W2) plano isolado de UX-09 (hooks por ciclo, serviços de intervalo, pagamento por ocorrência, atualização das guardas de ciclo) **sem mudança visual**; (W3) Transações, Contas Fixas e Casal em paralelo; (W4) Calendário (dividido em leitura e CRUD), depois as 4 telas pós-sketch e o fechamento com auditoria 360/390px.

### Pattern 1: Janela de ciclo estável (evita laço de refetch)
**What:** `cycleFor(person)` devolve objeto novo a cada tique do `now` (`useNow(60_000)`). Hooks de dados devem depender de `cycle.key` + `cycle.salaryDay`, nunca do objeto. O padrão já existe em `useCycleBudget` (estado `stable`).

### Pattern 2: Contas por ocorrência, pagamento pelo mês da ocorrência
**What:** itens vêm de `billsForCycle({ bills, payments, cycle })`; cada item tem `occurrence: {year, month, day}`; marcar paga usa `markAsPaid(item.billId, item.occurrence.month, item.occurrence.year, ...)` (é o que a Home faz em `HomeSections.onMarkPaid`). Uma conta pode ter 0, 1 ou 2 ocorrências no ciclo (`billOccurrences`).
**When to use:** Contas Fixas, camada de contas do Calendário, Casal (se mostrar).

### Pattern 3: View-model puro + `useMemo`
**What:** `buildDayModels({ cycleWindow, transactions, billItems, savings, contributions, notes, events })` devolve `Map<'YYYY-MM-DD', DayModel>` (itens ordenados, líquido em centavos, cores de ponto, post-its). O mapa de calor é `heatLevels(valores)` sobre os dias do mês exibido. Componentes só leem o `Map`; células em `React.memo` recebendo o `DayModel` do dia (referência estável enquanto os dados não mudam).

### Pattern 4: Recolhimento como redutor puro + flag `prog` em ref
**What:** estado `{ collapsed, lock }` mutado só por `collapseReducer(state, action)`; ações `scroll(top)`, `toggle`, `reset`. A regra copia o sketch: recolhe se `top > 24` e não há `lock`; reabre se `top <= 0` (e limpa `lock`); com `lock` e `top <= 0` só limpa o `lock`; `toggle` inverte e `lock = !collapsed`. O hook ignora eventos de `scroll` enquanto `progRef.current` for verdadeiro; `progRef` volta a `false` ~120ms depois (igual ao sketch) via `setTimeout`/`requestAnimationFrame`. `setState` com o mesmo valor não re-renderiza, então rolar sem cruzar limiar não causa laço. Listener `passive` no contêiner.

### Pattern 5: Sheet de ações da linha
**What:** um `RowActionsSheet` único (título, subtítulo, valor, ações em linhas de 56px: Marcar/Desmarcar paga, Editar, Apagar) reaproveitando `Sheet`; "Apagar" troca o conteúdo do mesmo Sheet por confirmação (`Cancelar` / `Apagar`), como no sketch 013. Reuso em Transações, Contas Fixas, post-its e eventos.

### Anti-Patterns to Avoid
- **`useCycleMonth` + `getTransactions(person, month)` nas telas redesenhadas:** reintroduz a aproximação; remover o hook e `src/lib/cycleMonth.ts` e atualizar as guardas.
- **`date-fns` (`startOfMonth`, `isToday`, `format(...,'yyyy-MM-dd')`) para limites e chaves de dia:** usa o fuso do host. Usar `zonedParts`/`dayKeyOf`.
- **`window.confirm` para apagar (hoje no Calendário):** substituir pelo Sheet de duas etapas (D-03).
- **Contas no Calendário por "número do dia" em toda célula** (`fixedExpenses.filter(fe => fe.dueDay === dayNum)` em `MonthCalendar.tsx:108`): repete a conta em células de meses vizinhos; usar a ocorrência.

### 5. Contas Fixas: ordem (D-14) e status (D-15)

**Ordem das categorias.** `categoryDefs` é um array de `{ id, name, color?, archived?, icon?, kind? }` (`shared/core/categories.js:12`). `reconcileCategoryDefs(names, defs)` (`:250`) devolve `buildCategoryDefs(list, defs)` (que preserva a ordem de `defs` e **acrescenta nomes novos no fim**) com `archived` recalculado; `archiveCategory` só marca `archived: true` (nunca remove nem reordena) (`:236-239`); `addCategory` reativa uma arquivada de mesmo nome sem mover (`:165-166`). Portanto **a posição no array é estável** e é a ordem do dono. `categoryDisplayName(item, defs)` resolve por `categoryId` e cai no texto legado (`:274-280`). `[VERIFIED: leitura de categories.js]`

**Regra determinística (`groupBillsByCategory`, pura):**
1. Resolver a categoria de cada item: `categoryId` -> def; senão `resolveCategoryId(category, defs)`; senão "legada" (texto sem def).
2. Ordem dos grupos: defs **ativas** na ordem do array; depois defs **arquivadas** na ordem do array; depois categorias legadas por ordem alfabética do texto normalizado (`normalize` de `classify.js`).
3. O conjunto de grupos e a ordem são calculados **sobre todos os itens** (não sobre os filtrados); o filtro (Todas/Pendentes/Pagas) apenas esconde linhas e descarta grupos que ficaram vazios, preservando a posição relativa. Assim marcar paga, trocar filtro ou desmarcar nunca reordena.
4. Dentro do grupo: data da ocorrência ascendente; empate por nome (localeCompare) e depois `billId` (estável).
5. Cabeçalho do grupo: "X de Y pagas" e subtotal usam **todos** os itens do grupo, não só os filtrados (como no sketch: `a = all[c]`).
Casos de teste: marcar paga não muda a ordem; filtro Pendentes é subsequência da ordem Todas; categoria arquivada vai depois das ativas; texto legado por último; dois meses no mesmo ciclo.

**Status.** A regra mora hoje em `FixedExpenseList.getStatus` (`FixedExpenseList.tsx:39-45`): paga -> `'paid'`; `dueDay < today` -> `'overdue'`; `dueDay <= today + 3` -> `'due-soon'`; senão `'pending'`, com `today = getDate(new Date())` (`:31`). Mover para `billStatus(occurrence, paid, todayParts)` no núcleo comparando datas (ver seção 1). O chip "hoje" é o caso `diff === 0`; "em breve" é `1..3`; "vencida" é `< 0` e nunca para item pago. Texto de apoio do sketch: "Venceu dia N · X dias de atraso", "Vence hoje", "Vence amanhã · dia N", "Vence dia N · em X dias" (derivar da diferença de datas, pluralizar com `plural` de `format.js`).

**Totais (três cartões).** Hoje `total = Σ expense.amount`, `paid = Σ payments`, `pending = total - paid` (`useFixedExpenses.ts:122-126`). Com ocorrências: `billsSummary(items)` com `plannedTotal`, `paidTotal`, `pending`, `paidCount`, `count`, derivado dos mesmos `BillItem` da Home. `billsForCycle.totalCents` usa `costCents` (valor pago se pago, senão planejado), que difere de `plannedCents` quando o valor pago é editado; decidir qual vai no cartão "Total mensal" e testar que Home e Contas Fixas mostram o mesmo número.

## Common Pitfalls

### Pitfall 1: Laço de refetch por dependência no objeto do ciclo
**What goes wrong:** a lista pisca e refaz a consulta a cada minuto (ou em loop).
**Why it happens:** `cycleFor(person)` devolve objeto novo a cada tique de `useNow(60_000)` (`CycleContext.tsx:34`).
**How to avoid:** depender de `cycle.key` + `cycle.salaryDay` (Pattern 1); `dataVersion` para recarregar após gravação.
**Warning signs:** `useEffect` com `cycle` ou `cycle.start` (Date) nas dependências; DOM mutando parado (o quick mediu "0 mutações em 3s").

### Pitfall 2: Chave de pagamento no mês errado
**What goes wrong:** Home mostra "paga" e Contas Fixas "pendente" (ou o contrário) quando o ciclo cruza dois meses.
**How to avoid:** `markAsPaid`/lookup sempre por `occurrence.month/year`; teste de concordância Home x Contas Fixas.

### Pitfall 3: Palavra `fixedExpense` no núcleo
**What goes wrong:** `npm run test:static` falha em `fixed-expense-manual.test.js:61`.
**How to avoid:** nomes `bill*` em `shared/core`; nunca importar tipos `FixedExpense` ali.

### Pitfall 4: Guardas coladas ao texto dos arquivos
**What goes wrong:** reescrever `NavRail`, `CouplePage`, `CalendarPage`, `FixedExpenseList`, `useFixedExpenses`, `TransactionsPage` quebra regex (tabela da seção 3).
**How to avoid:** cada plano lista as guardas que toca e as atualiza **no mesmo commit**; rodar `npm run test:static` após cada tarefa.

### Pitfall 5: Escala tipográfica
**What goes wrong:** executor copia `13px`/`peso 800` do sketch e a guarda `phase3-final` "(h)" falha nos arquivos listados (ou, nos arquivos novos, a UI diverge do padrão da Home).
**How to avoid:** UI-SPEC 03.1 decide a escala antes de implementar; guarda nova `phase3-1-*` com a escala escolhida.

### Pitfall 6: Percentil com empates e poucos dados
**What goes wrong:** poucos dias gastadores ou valores iguais colapsam todos os níveis em `h1`.
**How to avoid:** regra explícita para `n < 4` e empates em `heatLevels` + testes (incluir o caso do sketch).

### Pitfall 7: Recolhimento que se realimenta
**What goes wrong:** o mês recolhe, o contêiner da agenda cresce, o navegador ajusta `scrollTop`, dispara `scroll`, e o mês reabre.
**How to avoid:** histerese 24px/0 do sketch, `prog` em ref durante rolagem programática, redutor que devolve o **mesmo objeto** quando nada muda, listener passivo, sem leitura de layout no render.

### Pitfall 8: Altura da página do Calendário
**What goes wrong:** `100dvh` + `TopBar` + dock deixam a agenda sem espaço em 360x640 ou com rolagem dupla.
**How to avoid:** um só contêiner rolável; medir em 360x640 e 390x844; plano B sticky.

### Pitfall 9: Escrita no perfil do parceiro
**What goes wrong:** os Sheets novos (marcar paga, editar, apagar, post-it, evento) deixam o parceiro em somente leitura editar; a Home/LaunchSheet já bloqueiam, as telas legadas não.
**How to avoid:** `useReadOnly().guard('editar')` antes de toda mutação nas telas novas.

### Pitfall 10: Ramo `MOCK` esquecido
**What goes wrong:** o harness de layout e o `npm run dev` com `VITE_USE_EMULATOR=true` quebram em serviço novo sem ramo `MOCK`.
**How to avoid:** todo serviço novo copia o padrão `if (MOCK) { … mList … }` (ver `getTransactionsInRange`).

### Pitfall 11: Leituras em excesso (cota do Spark)
**What goes wrong:** `getAccumulatedBalance` lê todas as transações a cada busca; Relatórios faz N consultas por série.
**How to avoid:** saldo total sob demanda; uma consulta por janela larga nos gráficos.

### Pitfall 12: "Mês" do Casal igual ao mês de início do ciclo
**What goes wrong:** depois do dia do salário o "mês atual" mostra o mês passado.
**How to avoid:** `monthRangeOf` do mês-calendário de `now` deslocado pelo `offset` (seção 2).

### Pitfall 13: Rolagem horizontal "falsa" na auditoria
**What goes wrong:** a auditoria acusa overflow nos carrosséis intencionais (dock e chips) ou deixa passar um overflow real.
**How to avoid:** medir `document.documentElement.scrollWidth <= clientWidth` e listar elementos cujo `getBoundingClientRect().right > innerWidth` **fora** de contêineres `overflow-x: auto` conhecidos.

export function collapseReducer(state, action) {
  switch (action.type) {
    case 'scroll': {
      const top = action.top
      if (!state.collapsed && !state.lock && top > COLLAPSE_AT) return { collapsed: true, lock: false }
      if (state.collapsed && top <= 0) return { collapsed: false, lock: false }
      if (!state.collapsed && state.lock && top <= 0) return { collapsed: false, lock: false }
      return state // mesma referência: nada re-renderiza
    }
    case 'toggle': return { collapsed: !state.collapsed, lock: state.collapsed } // abrir (collapsed->false) liga o lock
    case 'reset': return { collapsed: false, lock: false } // trocar de período
    default: return state
  }
}

function center(nav: HTMLElement, el: HTMLElement, smooth: boolean) {
  const l = el.offsetLeft - 6
  const r = el.offsetLeft + el.offsetWidth + 6
  const v0 = nav.scrollLeft
  const v1 = v0 + nav.clientWidth
