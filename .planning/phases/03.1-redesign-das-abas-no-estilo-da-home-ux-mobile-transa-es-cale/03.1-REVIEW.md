# Fase 3.1: Relatório de revisão de código

**Revisado:** 2026-11-19
**Profundidade:** standard
**Arquivos revisados:** 77
**Status:** issues_found

## Resumo

Foram lidos os 77 arquivos da lista. `tsc --noEmit -p tsconfig.app.json` e `eslint` nos arquivos de `src/` passaram sem erros, então os achados abaixo são de lógica, concorrência, privacidade e acessibilidade, não de tipagem. Os itens que o dono declarou como aceitos (Porquinho `useSavings.add` sem id gerado no cliente, UAT humano em 360px, Calendário abrindo recolhido em tela baixa) não foram reportados.

O que está sólido: o núcleo puro (`cycle.js`, `billGroups.js`, `calendarModel.js`, `couple.js`, `series.js`, `heat.js`, `collapse.js`) tem limites inclusivos corretos, dinheiro em centavos inteiros e chaves de dia em São Paulo; o pagamento de conta é casado e gravado pelo mês e ano da ocorrência; todos os serviços novos usam `ownerScope()`/`ownerId()` e os índices compostos existem em `firestore.indexes.json`; não há `dangerouslySetInnerHTML`, `console.*` com dados nem `window.confirm` nos arquivos revisados; os hooks por ciclo descartam respostas velhas por contador e só expõem dados cuja chave bate com o ciclo atual.

Os pontos de maior risco são: (1) a edição de meta regrava `currentAmount` com o valor de tela, o que pode apagar aportes feitos em paralelo; (2) `BankConnections` é a única caixa de Configurações que ignora o modo somente leitura e deixa remover, conectar e sincronizar bancos com o perfil do parceiro; (3) vários pontos em que o dia de São Paulo é trocado pelo fuso do aparelho (`dateOfKey`, `formatDate`), que os testes do núcleo em `UTC` e `Asia/Tokyo` não pegam.

## Critical Issues

### CR-01: Editar uma meta regrava `currentAmount` com o valor da tela e pode apagar aportes

**File:** `src/components/goals/GoalForm.tsx:118-124` (consumido por `src/pages/GoalsPage.tsx:75-79` e `src/services/goals.service.ts:96-98`)
**Issue:** Na edição, `data` leva `currentAmount: goal?.currentAmount ?? 0`, onde `goal` é o objeto guardado em `editing` no momento em que o Sheet abriu. `updateGoal` faz `updateDoc` com esse campo. `addContribution` incrementa `currentAmount` dentro de uma transação no servidor, então o valor da tela fica velho assim que o outro celular do casal aporta, ou assim que uma sincronização muda o documento. Cenário: Ela abre "Editar" em "Viagem" (currentAmount R$ 500). Ele aporta R$ 200 no outro celular (documento vai a R$ 700). Ela troca só o nome e salva; o documento volta a R$ 500, e o histórico de aportes (`goalContributions`) passa a somar R$ 200 a mais do que a meta mostra. É perda de dado monetário sem aviso.
**Fix:** A edição não deve enviar `currentAmount`. Só o fluxo de aporte altera esse campo.
```tsx
const data: GoalFormData = {
  name: cleanName,
  targetAmount: fromCents(cents),
  ...(goal ? {} : { currentAmount: 0 }),
  ...(deadlineDate ? { deadline: deadlineDate } : {}),
  person: goal?.person ?? person,
}
```
(ajustar o tipo para `Partial<...>` na edição, ou separar `GoalCreate` e `GoalEdit`).

### CR-02: `BankConnections` ignora o modo somente leitura e a regra "só a própria pessoa edita" das outras caixas de Configurações

**File:** `src/components/settings/BankConnections.tsx:54-126, 198-236`
**Issue:** Reconectar, desconectar (`askRemove`/`confirmRemove`, linha 113), conectar banco para qualquer pessoa (linha 54) e "Sincronizar agora" (linha 101) não passam por `useReadOnly().guard` nem checam `readOnly`. Todas as irmãs (`NotificationsCard`, `AppearanceCard`, `CycleIncomeCard`, `CategoriesCard`, `CategoryEditorSheet`) bloqueiam com `readOnly` e as que são por pessoa também com `user.person !== person`. Resultado: com o perfil do parceiro em vista (`readOnly === true`), é possível tocar em "Desconectar" e remover a conexão bancária, ou iniciar "Conectar banco (Ela)" estando logado como "Ele". O foco desta revisão exige que nenhuma escrita seja alcançável com o perfil bloqueado. O arquivo foi o último editado (G-01) e o novo Sheet de confirmação herdou a lacuna.
**Fix:** Usar `useReadOnly` e, para as ações por pessoa, a mesma regra das irmãs.
```tsx
const { readOnly, guard } = useReadOnly()
const { user } = useAuth()
const canAct = (person: PersonType) => !readOnly && (!user || user.person === person)

const askRemove = (c: BankConnection) => {
  if (guard('editar')) return
  setRemoveFailed(false)
  setPendingRemoval(c)
}
// connect/reconnect/sync: `if (guard('editar')) return` no começo; botões com aria-disabled e dica de leitura.
```

## Warnings

### WR-01: Desmarcar conta paga pode ser revertido por uma consulta velha (a UI volta a mostrar "paga")

**File:** `src/hooks/useCycleBills.ts:115-133`
**Issue:** No ramo de desmarcar, a atualização otimista remove o pagamento e depois chama `unmarkAsPaid`; ao terminar, não há refetch nem invalidação (`latest.current += 1`) de consulta em andamento. Cenário: o usuário marca a conta A (a página chama `bumpData()`, que dispara uma consulta); logo depois desmarca a conta B. Se a resposta da consulta disparada antes do `deleteDoc` chegar depois do `patchPayments`, ela entra por `setLoaded` (o contador `latest` ainda bate) com o pagamento de B incluído. A tela volta a mostrar B como paga embora o servidor já tenha apagado o documento, e nada corrige isso até a próxima consulta. O ramo de marcar não tem o problema porque termina com `await fetchData()`.
**Fix:** Invalidar consultas em andamento antes da escrita e reconciliar depois.
```ts
latest.current += 1                 // antes do patch otimista, nos dois ramos
patchPayments(...)
await Promise.all(existing.map((p) => unmarkAsPaid(p.id)))
await fetchData()                   // reconcilia com o servidor, como no ramo de marcar
```

### WR-02: Meta com 99,5% ou mais é mostrada como "Concluída" e perde o botão Aportar

**File:** `src/components/goals/GoalCard.tsx:19-35, 73-95`; `src/components/goals/GoalDetailSheet.tsx:39, 61`
**Issue:** `isComplete = percentage >= 100`, e `percentage` vem de `Math.round`. Com alvo R$ 1.000,00 e R$ 995,00 guardados, `Math.round(99.5) === 100`: o cartão mostra "Meta atingida" e "Concluída", esconde "Faltam R$ 5,00" e remove o botão "Aportar", embora faltem R$ 5. Para metas grandes a falta escondida passa de R$ 50. A própria `GoalsPage` usa `current.currentAmount < current.targetAmount` (linha 187) para oferecer "Aportar", então a tela se contradiz.
**Fix:** Decidir conclusão em centavos, não pelo percentual arredondado.
```ts
const isComplete = toCents(goal.currentAmount) >= toCents(goal.targetAmount)
const percentage = isComplete ? 100 : Math.min(99, goalPercentage(goal))
```

### WR-03: `addContribution` soma reais em ponto flutuante e grava o resultado na meta

**File:** `src/services/goalContributions.service.ts:110, 126-130`
**Issue:** `newAmount = currentAmount + amount` soma reais (`fromCents(cents)`) em `number` e grava no documento. Isso quebra a regra de dinheiro em centavos inteiros: `0.1 + 0.2` vira `0.30000000000000004`, e somas repetidas acumulam resíduo no `currentAmount`. A exibição esconde o resíduo por `toCents`, mas comparações cruas como `currentAmount < targetAmount` (`GoalsPage.tsx:187`) podem errar por 1e-16 e oferecer "Aportar" numa meta já cheia, ou o contrário.
**Fix:**
```ts
const newAmount = fromCents(toCents(currentAmount) + toCents(amount))
```
(importar `fromCents` e `toCents` de `@shared/core/ledger.js`; aplicar também no ramo MOCK.)

### WR-04: "Saldo total acumulado" fica velho depois de editar, apagar ou lançar na mesma tela

**File:** `src/components/transactions/TransactionTotals.tsx:39-47`; `src/pages/TransactionsPage.tsx:110-115`
**Issue:** O acumulado é buscado uma vez, na primeira abertura de "Detalhes", e guardado em `accumulated`. A `key` do componente é `${person}:${cycle.key}`, que não muda quando uma transação é editada, apagada ou criada no mesmo ciclo (`bumpData`). Cenário: o usuário abre Detalhes e vê R$ 4.200,00 acumulados, apaga um gasto de R$ 300; "Saldo do ciclo" muda e o acumulado continua R$ 4.200,00 até trocar de ciclo ou de pessoa.
**Fix:** Incluir o `dataVersion` na `key` (ou resetar `accumulated` para `idle` quando `totalsCents` mudar) e refazer a consulta se Detalhes estiver aberto.
```tsx
const { now, bumpData, dataVersion } = useCycle()
<TransactionTotals key={`${person}:${cycle.key}:${dataVersion}`} ... />
```

### WR-05: `dateOfKey`, `noon` e `dayLabel` usam o fuso do aparelho e gravam post-its e eventos no dia errado

**File:** `src/pages/CalendarPage.tsx:26-29, 332, 342`; `src/components/calendar/NoteSheet.tsx:44-51`; `src/components/calendar/EventSheet.tsx:40-47`
**Issue:** `dateOfKey` faz `new Date(year, month - 1, day, 12)` (meio-dia local) e o Sheet reaplica `noon` com `getFullYear/getMonth/getDate` locais. O calendário agrupa por `dayKeyOf` em São Paulo. Para um aparelho a leste de UTC+9 o meio-dia local cai antes da meia-noite de São Paulo do dia anterior. Verificado com `node`: em `Australia/Sydney` e `Pacific/Auckland`, `dayKeyOf(new Date(2026, 10, 19, 12))` devolve `2026-11-18`. Cenário: viajando, a pessoa toca no dia 19 e salva o post-it; ele aparece no dia 18. `Asia/Tokyo` passa por coincidência (meio-dia JST é exatamente 00:00 de São Paulo), que é justamente um dos fusos dos testes. O mesmo código existe em `TransactionEditSheet`/`SavingsForm`/`GoalForm`, que usam o caminho certo (`zonedTimeToInstant(y, m, d, 12)`).
**Fix:** Construir o instante em São Paulo e formatar o rótulo por `zonedParts`.
```ts
import { zonedTimeToInstant } from '@shared/core/time.js'
function dateOfKey(key: string): Date {
  const [y, m, d] = key.split('-').map(Number)
  return zonedTimeToInstant(y, m, d, 12)
}
// Nos Sheets: remover noon() e usar `date` como veio; dayLabel via zonedParts(date).
```

### WR-06: `formatDate` do app usa o fuso do aparelho e mostra o prazo da meta um dia depois

**File:** `src/components/goals/GoalCard.tsx:55`; `src/components/goals/GoalDetailSheet.tsx:63, 103`; `src/lib/utils.ts:15-17`
**Issue:** `GoalForm` grava o prazo como meio-dia de São Paulo (15:00 UTC) e lê de volta por `zonedParts`. `GoalCard` e `GoalDetailSheet` formatam com `Intl.DateTimeFormat('pt-BR')` sem `timeZone`. Verificado em `Asia/Tokyo`, `Australia/Sydney` e `Pacific/Auckland`: o instante `2026-11-19T15:00:00Z` aparece como `20/11/2026`, enquanto o formulário mostra 19/11. Os aportes (`formatDate(c.date)`, data real do toque) têm o mesmo desvio perto da meia-noite.
**Fix:** Formatar pelo dia de São Paulo: `dayMonth(zonedParts(date))` com o ano, ou passar `timeZone: 'America/Sao_Paulo'` em `formatDate`.

### WR-11: Não dá para remover o prazo de uma meta na edição

**File:** `src/components/goals/GoalForm.tsx:122`; `src/services/goals.service.ts:96-98`
**Issue:** `...(deadlineDate ? { deadline: deadlineDate } : {})` omite o campo quando o usuário esvazia a data, e `updateGoal` só altera as chaves presentes (`updateData = { ...goal }`; `deadline` só é convertido quando truthy). ### WR-12: Aporte em meta pode duplicar e incrementar duas vezes em falha ambígua de rede

**File:** `src/services/goalContributions.service.ts:118-146`; `src/components/goals/ContributionForm.tsx:76-85`
**Issue:** O id do aporte é gerado dentro da transação (`doc(collection(db, COL))`) e o formulário mostra "Não foi possível salvar" quando a promessa rejeita. Se o commit chegou ao servidor mas a resposta se perdeu, o usuário toca de novo e o aporte é gravado duas vezes, com o `currentAmount` da meta somado duas vezes (não há deduplicação). A exceção documentada como aceita cobre só `useSavings.add` do Porquinho; os lançamentos e o Porquinho recebem id no cliente (WR-08) e os aportes de meta, não.
**Fix:** Gerar o id uma vez por abertura do formulário (como `newTransactionId`), usar `doc(db, COL, id)` e, dentro da transação, `if ((await transaction.get(contributionRef)).exists()) return id` antes de somar.

### WR-13: Foco se perde ao tocar em "Manter" na confirmação de apagar

**File:** `src/components/ui/row-actions-sheet.tsx:149`; `src/components/calendar/NoteSheet.tsx:216`; `src/components/calendar/EventSheet.tsx` (botão "Manter")
**Issue:** A confirmação troca o conteúdo do mesmo Sheet e move o foco para "Manter" (`keepRef`). Ao tocar em "Manter", `setConfirming(false)` desmonta o botão focado e o foco cai no `body`: leitor de tela perde o contexto e quem usa teclado precisa de Tab para voltar ao Sheet (o trap só recupera no próximo Tab). O mesmo vale para o erro de apagar, que mantém o foco em botões desabilitados durante `deleting`.
**Fix:** Ao voltar da confirmação, devolver o foco ao gatilho de origem (`data-autofocus` do primeiro item ou ref do botão "Apagar").
```tsx
const askRef = React.useRef<HTMLButtonElement>(null)
// ao cancelar:
setConfirming(false); requestAnimationFrame(() => askRef.current?.focus())
```

### WR-14: Conta fixa nova aparece "vencida" e não paga em todos os ciclos passados
